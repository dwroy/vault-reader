# Vault Reader architecture

Status: M1b implementation candidate, 2026-09-22. Product baseline: Vault Reader design v1. Platform order confirmed by the owner: **iOS first, Android second**.

## Three boundaries

```text
                 Shared reader-web (JavaScript + CSS)
          Markdown / wikilinks / anchors / sanitization / typesetting
                                  |
                  contracts/reader-v2.d.ts (version 2)
                       /                         \
            iOS native host                 Android native host (future)
     SwiftUI / WKWebView / QuickLook     Compose / WebView / system viewers
     VaultCore Swift package            Kotlin data adapters
     URLSession / disk / Keychain        HTTP / disk / Keystore
```

`packages/reader-web` has no UIKit, WebKit, Swift or Android dependency. It receives raw Markdown and a tree; it returns rendered content and three messages (`open`, `preview`, `height`). It does not fetch GitHub, persist app settings, navigate native screens, access tokens or manage downloads. The same bundled JS/CSS will ship in both apps. No CDN at runtime. The owner subsequently requested saved repositories and GitLab support during M1b; these extensions do not change the shared bridge.

`packages/contracts/reader-v2.d.ts` is the current platform contract; v1 remains as the historical interface. Local files are repository-relative UTF-8 paths, not platform filesystem URLs. SHA identifies content; path identifies a note. The native host supplies resource URLs: `vault://file/` on iOS; Android should use [WebViewAssetLoader](https://developer.android.com/develop/ui/views/layout/webapps/load-local-content) and an origin-scoped [message listener](https://developer.android.com/develop/ui/views/layout/webapps/native-api-access-jsbridge), after its own storage/origin probe. Navigation links stay `vault://f/<encoded-path>#<anchor>` as a logical route; the native host interprets them. The native bridge adapter lives in `RendererWebView.swift`; the shared renderer never calls `window.webkit` directly.

`packages/VaultCore` is the **Apple implementation**, not an Android-shareable core. It has Foundation/CryptoKit and no SwiftUI, UIKit, WebKit, Security or QuickLook. Models, GitHub transport, tree indexes, cache integrity and metadata can be tested without an iOS simulator. Android will implement the small data layer in Kotlin against the same behavior below. Native UI, storage/security and system integration are separate on each platform. Do not introduce Kotlin Multiplatform, Rust FFI or a second app during M1 merely to maximize code sharing. If native sync logic grows materially during Android development, revisit sharing then, based on measured duplication.

## Data invariants for both apps

- Read-only GitHub/GitLab REST requests; four concurrent requests globally, cancellable, explicit ETag/304 handling. Never send credentials to a renderer or external host.
- Branch head → complete recursive tree → immutable blob SHA. GitLab uses the pinned head commit as the tree revision, because its branch API does not expose a root-tree SHA. Reject truncated trees and keep the previous complete metadata.
- Verify Git blob SHA-1 (`blob <byte length>\0` + bytes) before writing. Refuse files over 100 MiB.
- Per-repository blobs; per-branch metadata. On iOS these directories use SHA-256 of the repository identity / branch, avoiding unsafe filenames and cross-repository collisions.
- Atomic writes; exclude renewable blobs from backup; device file protection on iOS. Native credential store keyed by service and repository; Android must use Keystore-backed credential encryption.
- Access-time eviction, default 500 MiB. Downloaded Markdown/SVG remain pinned even when over the limit. QuickLook copies survive automatic eviction while they may be in use; closing the preview removes its copy, and explicit attachment cleanup removes any leftovers. The just-requested blob is retained through preview preparation even if pinned Markdown already exceeds the cache limit.
- Network failure keeps cache readable. 401 clears the active credential and opens settings; 403 permission denied is distinct from quota exhaustion. Editing settings validates the new credentials/tree before replacing the active repository.
- Path traversal cannot escape the vault; there is no `file://` path crossing the JS bridge.

## Current iOS implementation

`AppState` coordinates startup, refresh, repository changes and visible status. `RepositoryLibrary` saves credential-free profiles and migrates the old active GitHub configuration without changing its cache/Keychain key. The Directory menu and Settings switch profiles, reset all navigation stacks, restore the selected branch’s prepared search text and retain each repository’s disk cache. Requests capture their original client before suspending so a rapid switch cannot send them through another repository’s credentials. `VaultCore` owns transport/cache/index operations; `SchemeHandler` supplies bundled assets and cached/downloaded files. `RendererWebView` handles bridge validation, native pull-to-refresh, Dynamic Type and scroll restoration. `NoteView`/`DirView` own navigation and preview presentation. `SettingsView` uses Keychain through the iOS-only credential adapter.

The bundled renderer uses markdown-it, DOMPurify, footnotes and task lists. Noto Sans SC Variable (OFL, approximately 4.5 MiB) is bundled with Unicode-range font subsets for offline Chinese rendering on both platforms. The iOS simulator exhibited missing CJK glyphs with system-only CSS; a local font fixed the verified screenshot without depending on system font downloads. Source is in `packages/reader-web/src`; generated bundle and license notices are committed under `VaultReader/Resources/renderer`. Run `npm ci && npm run build:renderer` after source changes. The bundle is reusable by Android; packaging into Android assets is deferred until that app exists.

The current UI opens Directory, followed by Reading, Recent and Search in the tab bar. The Directory root keeps its project switcher on the leading side and an ellipsis action menu with Refresh and then Settings on the trailing side. Subdirectories retain the back button and the same trailing menu; note actions stay in their existing ellipsis menu. Reading has its own navigation stack: saved project (repository/branch), project library, then a document. Choosing a project activates its existing connection; progress remains scoped to that project. Reading tabs retain independent navigation stacks. Settings is a sheet over the current stack, opened from the Directory ellipsis menu, initial setup or the project switcher’s Add vault action, so closing it with Done preserves the current location. Successful connection or profile selection returns to Directory. There is no Home tab or required home-file input; a complete repository tree is sufficient to connect. The legacy home field remains decodable for saved-profile compatibility and prefetch priority. Foreground Markdown completion starts after repository startup and refresh without waiting for a home document to render. Recent loads 30 commits with branch-scoped ETag caching. Expanded commit files are fetched lazily and paginated to GitHub's 3,000-file endpoint cap; capped results are marked incomplete. File links open the current branch version; deleted/missing paths are disabled. Rename metadata and complete commit messages remain visible. See the [GitHub commit API](https://docs.github.com/en/rest/commits/commits#get-a-commit).

Search is local and isolated by repository/branch. `SearchIndex` owns the active catalog and published prepared text; a separate serial `SearchPreparationWorker` handles projection, folding and derived-cache IO. Queries scan immutable snapshots in cancellable detached tasks, so a Markdown parse or cache write does not hold the query actor. Catalog preparation also runs outside the main actor. Existing prepared text remains searchable during incremental work; a new vault gets metadata results after its catalog is ready and body results progressively. Revision/epoch checks discard cancelled or obsolete work after refresh or a vault switch. Foundation parser and regular-expression calls themselves are not preemptible; their input size is bounded. Each document preparation/cache restore and detached catalog/query operation drains its Foundation autorelease pool before returning, so temporary Objective-C objects cannot accumulate across a busy cooperative executor.

Every file can match its name, path, extension, inferred type/MIME aliases, known tree byte size and a SHA prefix of at least seven characters. The app does not download attachments to extract metadata or invent unavailable author/date/EXIF fields. Body preparation accepts UTF-8 `.md`, `.txt` and `.text` files with at most **512 KiB** source data. Known oversized files and other formats are metadata-only from the catalog. Cached source sizes are checked before reading; GitHub/GitLab raw downloads cancel when reported or received bytes exceed the same limit, including unknown-length transfers, and validate the temporary file size before loading it. Transport may receive a final chunk beyond the threshold. Explicit file opening retains the separate ordinary file limit.

The body plan admits at most **5,000 distinct text-kind/SHA pairs**, ordered by the legacy preferred home path then path; duplicates share one prepared body. A prepared document has a **2 MiB accounted payload limit**, and all retained bodies share a **32 MiB accounted payload budget**. Accounting conservatively includes original/folded text and checkpoints; these values are not an OS/process memory ceiling. Catalogs, parser/cache temporaries, concurrent query snapshots, WebKit and attachments consume additional memory. When a budget is reached, remaining bodies become metadata-only; already prepared bodies and all metadata stay available. Size, encoding and per-document exclusions are persisted so a restart does not keep downloading/rebuilding them. A tree/limit change can reconsider eligibility; aggregate capacity exclusions are recomputed rather than permanently cached.

Whitespace-separated query terms use AND semantics across name, body and metadata. Case/diacritic folding is done at ingestion, with UTF-8 byte scans per query. Results rank exact filenames (with or without extensions), filename prefixes, all filename terms, partial filename matches, body matches, then path/metadata-only matches; ties use the path. The UI keeps the best 200 matches and reports the total, with a refinement hint when capped. Dot-file filtering happens before the cap. Sparse folded-to-original checkpoints provide short original-spelling snippets. Input/context changes use a 120 ms debounce and cancel stale queries; indexing progress requests a coalesced follow-up refresh without cancelling the query already in flight, allowing its first result to publish.

`MarkdownSearchText` uses Foundation's Markdown parser plus common Obsidian projections (wikilink labels, highlights, comments). It excludes frontmatter and link destinations and preserves fenced/inline code. This is a practical text projection, not a second Obsidian renderer or a claim of full syntax parity. Plain text is indexed literally. PDF/HTML/image and other attachment contents are not indexed. Native snippets highlight query terms; Markdown results use the existing credential-free v2 `highlightSearch` / `scrollToSearchMatch` bridge to highlight across inline elements and reveal a body match. Rendered metadata is excluded and collapsed details open when targeted. The first 1,000 occurrences per page are marked. Search overrides a book bookmark on initial entry only; reflow and returning preserve the subsequent position. Metadata-only results use ordinary opening/restoration; TXT uses the existing attachment preview.

Search shows indexed/pending body counts separately from metadata-only files, with per-result reasons (type, size, encoding or capacity). Scope details expand from the count row; missing-body failures remain visible with Continue. A cancellable foreground task restores prepared text, rebuilds missing projections from verified cached blobs, then downloads missing eligible sources serially. Counts publish every 32 local documents or about 150 ms between operations, and after downloads. Missing/corrupt files do not block later files; service-wide failures stop for retry. Completion starts after startup/refresh or opening Search, pauses in the background and rejects stale publication. This is not M2 OS background refresh.

`VaultContentProfile` offers a conservative suitability hint by file count rather than byte volume, excluding dot-prefixed configuration paths. It warns when there are no recognized readable files, or at least five files are present and fewer than 25% are readable. Readable here includes recognized text (including HTML/code/data and PowerShell scripts) plus native PDF documents; PDF body indexing remains unsupported. This avoids treating note libraries with many illustrations as unsuitable simply because attachments exceed half the file count. Directory and Search both offer a 44-point close button. `VaultNoticePreferences` persists dismissal per repository/provider/branch on this device, separately from sample mode, so either page's dismissal hides both and survives restart/refresh. Other vaults are unaffected. The extension-based hint does not inspect file contents, block browsing or alter search coverage.

`SearchTextCache` schema 2 persists binary property-list envelopes keyed by **text kind + content SHA** under the repository's `search/<branch-key>/` directory; sample and real repositories use separate roots. Envelopes store schema, kind, source bytes, SHA and a SHA-256 payload checksum, with either prepared original/folded text and sparse byte offsets or an exclusion decision. Offset validation reconstructs fresh `String.Index` values without reparsing/folding. Old schema, wrong-SHA/kind, malformed/checksum/offset failures fall back to verified blobs. Bump the schema when projection, normalization or layout changes. Atomic writes use iOS file protection and exclude the directory from backup. Individual derived records are capped at **4 MiB**. Write failure preserves usable in-memory text and increments a content-free diagnostic counter.

The complete current tree supplies paths; the cache never supplies its own file list. Renames and duplicate kind/SHA pairs reuse preparation. Tree updates drop obsolete results and prune unreferenced or ineligible derived files without disturbing other branches. Derived disk usage remains separate from the blob/attachment storage counter and eviction budget. This is persistent bounded preparation with linear substring search, not an inverted index; no SQLite/FTS, tokenizer, renderer contract or network service was added.

A `WebViewContainer` can discard its actual WKWebView while SwiftUI retains the navigation shell. Each note visit keeps its own scroll offset; outgoing pages release WebKit and returning pages rerender. This uses less memory than retaining eight live pages. Font readiness waits are bounded and cancellable: an offscreen animation-frame promise would otherwise keep a WebView alive indefinitely. Hosted tests traverse twelve levels and measure live weak WebView references and restored offsets; physical-device limitations remain in ACCEPTANCE.md.

Attachments share a native preview destination across Directory/Search/Recent and an image-preview sheet from Markdown. Raw downloads report byte progress, can be cancelled, are size-limited, then hash-verified before caching. Files above 100 MiB offer a GitHub link. HTTP(S) links ending in mp4/mov/m4v use a native AVPlayer; other web links use Safari. Long real-vault video/PDF transfer acceptance is separate from synthetic QuickLook tests.

The Markdown note menu offers Share in both normal and book reading mode. The iOS host extracts plain text from the current sanitized article and presents `UIActivityViewController`. Headings, paragraphs, code and image descriptions are included; frontmatter/tags and hidden comments are omitted, and collapsed article details are included. Sharing uses the already loaded page, including offline pages, without fetching or publishing a repository link. Images and attachments are not exported. This native action does not change the shared renderer or bridge contract.

## Compact library status

Repository status lives in the native `LibraryStatus` value, with an explicit kind, full explanation and recovery action. Errors are classified from `VaultError`/`URLError`, never from translated text. Timeouts and other service failures show “Not updated”; only the network's explicit offline error shows “Offline”. Missing/invalid credentials and denied access lead to Settings, rate limiting offers retry, and file-specific failures retain their in-page recovery controls. Successful refreshes, including an unchanged/304 branch, clear the status.

`LibraryNavigationTitle` replaces the full-width status banner across Directory, Recent, Search and reading/file destinations. A small icon and caption follow the title; long titles, translated labels and accessibility sizes fall back to an icon with the full VoiceOver value. Short titles retain their center alignment. The minimum status hit target is 44 points. Tapping opens a native popover with the active repository, complete message and applicable Retry/Settings action. Accessibility text sizes use a scrollable sheet so the message and recovery actions remain reachable. Sample and local-cache modes use neutral indicators; ordinary success has no persistent badge. Detailed file errors, search coverage counts and form validation remain with the content or operation they describe.

This is host UI only: no renderer, bridge, credentials or VaultCore changes are required. Debug-only `--demo --status-preview` snapshots exercise the status presentation with synthetic data and do not make network requests.

## Security and host integration

Native code injects `VaultHost` at document start. It only exposes a resource URL prefix and the three message methods. Messages are accepted only from the renderer main frame at `vault://app`; their URLs/paths are checked against the current index. Navigation outside initial renderer loading is canceled and routed natively. Raw HTML documents use a separate WebView **without this bridge**. `HTMLLocation` hashes repository identity, branch and file path into a stable origin; a content update does not reset progress. A dedicated [persistent WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:)) keeps HTML storage apart from ephemeral Markdown views. The HTML scheme handler only accepts its own origin and canonical indexed paths, supplies relative resources, and rejects renderer/file hosts. It registers no scripts or message handlers. Explicit links to another vault file route natively, giving another HTML file its own origin.

DOMPurify removes executable markup and event attributes. Images allow only vault resources and HTTPS; style attributes are restricted to generated image widths, and SVG is never injected into the Markdown DOM. Code fences do not execute. Tree/Markdown are passed with `callAsyncJavaScript(arguments:)`, not interpolated into source code.

iOS 26.3 simulator probe passed: `localStorage` works at `vault://html-probe-a`, is invisible to host B, and survives recreation of a WebView at host A. M1b additionally verifies file/repository isolation with the production HTML configuration, and synthetic localStorage survives app termination/relaunch on both the simulator and iPhone. Android origin behavior remains untested. No inference of Android storage compatibility from this iOS result.

Reference: Apple's [custom scheme handler](https://developer.apple.com/documentation/webkit/wkurlschemehandler) and WebKit's [persistent data store profiles](https://webkit.org/blog/14423/building-profiles-with-new-webkit-api/). GitHub protocol follows its [Git blobs API](https://docs.github.com/en/rest/git/blobs).

## GitHub and GitLab adapters

`RepositorySource` is implemented by `GitHubClient` and `GitLabClient`. Their shared `RepositoryHTTP` sends only GET requests, bounds raw downloads, reports progress, refuses redirects to keep credentials on the configured endpoint, and provides one four-permit request gate across providers. GitLab sends `PRIVATE-TOKEN`; the UI recommends [read_api permissions](https://docs.gitlab.com/security/tokens/access_token_scopes/) with a project-scoped token where available. GitHub continues using its repository-scoped fine-grained token.

GitLab supports GitLab.com and HTTPS self-managed instances, including a URL subpath and nested namespaces. URLs with embedded credentials, query strings or fragments are rejected. Its [repository tree](https://docs.gitlab.com/api/repositories/) is read page by page at the immutable head; a 100,000-entry safety cap rejects the entire refresh, retaining previous complete metadata. Raw blobs are downloaded by SHA and verified with the same Git blob hash as GitHub. GitLab trees omit sizes, so size can be unknown until download. [Commit diffs](https://docs.gitlab.com/api/commits/#retrieve-commit-diff) may be limited by server configuration; the UI always discloses that limit and links to the commit rather than claiming completeness. Cross-vault `obsidian://` routing is still separate from saved repository switching.

## Reading extension requested by the owner

`BookCatalog` and Codable reading records live in VaultCore and contain no UI, Keychain or native file URLs. The native `ReadingStore` writes bounded history (200 documents per repository/branch) atomically with device file protection under Application Support, outside renewable content cache. Views capture their original store so a later project switch cannot save into the wrong vault. Original and condensed editions use their distinct indexed paths. Only indexed relative PDF links in reading-list Markdown are discovered; external targets and traversal are rejected.

The shared v2 renderer retains the original three host messages and adds host-neutral heading outlines, position capture/restore and reading styling. Duplicate headings receive distinct outline keys. Native Markdown reading restores a heading plus relative offset, with whole-document fraction as fallback if the heading disappears. It waits for a visible viewport and fonts before restoring. Book mode suppresses the ordinary renderer's delayed first-frame scroll, which could otherwise reset a restored location. HTML still registers no script or message bridge; its extra position tracking uses UIScrollView only. PDFKit remains native to iOS and never enters VaultCore or the shared renderer.

An explicit reading list takes precedence over folder guessing; the vault-independent format is specified in [READING-LIST.md](READING-LIST.md). The root README's `书单`/`booklist` frontmatter names the list files, so any layout works. Without that declaration, files named `书单.md`/`booklist.md` anywhere and top-level Markdown in reading folders are read. VaultCore's `BookList` parses each list: `##` headings are groups, `###` headings with at least one recognized `- key：value` item are books. Keys map to metadata (作者/评分/状态/备注) or file roles: 原书 (imported PDF), 全文 (organized full text), 精简版, 阅读器, 笔记, 评论 and 入口. Link resolution is a Swift port of the renderer's `tree.js`, so a wikilink or relative link resolves to the same file in the list and in the rendered note. HTTP(S) targets become external Safari links and are never fetched; other schemes and traversal are dropped. Unresolved targets remain visible as missing rows. When a list declares books, Reading groups them as declared, opens a per-book page ordered by role, and shows any reading-folder file the list does not mention under “not in the reading list”. Without a list, the folder catalog below still applies. Continue reading on the project page and recent reading in a project each list at most three Markdown documents; PDF and HTML progress is still stored (bounded history of 200) and shown on the book page.

Reading values cross the WebKit bridge as JSON strings, and a preference change captures, reflows and restores inside one page call. If WebKit loses the page process, or any render step fails, the renderer reloads once and restores the last saved position; only a repeated failure is shown, naming the failed step. On an iPhone running iOS 26.6.1, a call in flight while the page process died returned "JavaScript execution returned a result of an unsupported type", which previously surfaced as an alert over a blank page.

Markdown positions are persisted on settled scroll and release; page changes persist PDF progress. Font/theme settings are per document. Missing PDF outlines offer page entry instead of guessed chapter mappings. The existing 100 MiB transfer bound, hash validation, download cancellation and cache eviction policy apply. Progress is local, with no repository write or cross-device synchronization. Debug-only cache/open-file launch flags support private local acceptance without placing book contents or credentials in the app bundle.

## File display preferences

The native observable `FileDisplayPreferences` persists `hideDotFiles` in UserDefaults, defaulting to false. The list predicate checks every repository-relative path component, so a dot-prefixed directory also hides its descendants. Directory counts, reading catalogs/history, search results and commit-file rows use this preference. Filtering happens at presentation boundaries; the complete repository index, cache and link resolution remain available.

## International first release

The owner requested an English-default release supporting 12 interface languages, including Arabic, Hindi and Indonesian. The catalog in `localization/catalog.json` generates native `.strings` resources for the iOS host and separate Foundation-only repository-error resources for VaultCore. Locale matching handles SwiftPM's lowercase compound locale directories. Per-app language selection is provided by iOS; unsupported preferences fall back to English.

Only app chrome is localized. Repository identifiers, paths and document text are never treated as localization keys. An additive `reader-v2` localization method passes only a language tag and five translated labels, with English defaults for hosts that omit it. The renderer escapes labels before HTML insertion, sets generated UI direction after sanitizing, determines prose direction per block and isolates code left-to-right. Native semantic forward/backward symbols follow right-to-left layout.

English synthetic samples are used outside Chinese interfaces; existing Chinese fixtures remain available for Chinese and deterministic regression tests. All samples retain isolated cache and reading state. Full reviewed help and policy documents remain English/Simplified Chinese, with localized disclosure in other interfaces. No token or document is sent to a translation service. See `localization/README.md` for maintenance and verification.
